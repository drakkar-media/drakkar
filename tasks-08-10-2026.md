# Tasks 2026-10-08: health check audit follow-ups

Source: read-only audit of prod logs (last 24h) and DB on 2026-10-08. Nothing was changed on prod and no code was edited.

## Audit summary

- Symptom: some TV episodes and movies play for a few seconds and then stop. Resetting the item (new release) fixes it, but the periodic health check never flagged them.
- All 10,993 published items show `health_ok = true`, checked within the last day.
- Sampled full-length probe: 359 random published files, 11-12 offsets each from 0% to 99%, 256 KB reads through the real mount path. 358 passed. 1 stored_rar file returned 0 bytes at offset 0 (library_item_id 27120), then read fine on two retries. That is an intermittent bad article, which a single-shot check misses.
- Segment maps are consistent: for all 7,070 direct_nzb video files, segment count x decoded size matches the stored file size.

## Why the health check misses it

1. Deep check covers only the first segments, 12 magic bytes, and a ~16-48 MB ffprobe prefix. A file that is fine early and bad mid-file or at the tail passes.
2. A single read passes even when an article is flaky (wrong data on some fetches).
3. The ffmpeg decode-issue scan (`checkDecodeIssuesAdvisory`) is advisory only and does not blocklist.
4. Real playback read failures (`dav read error` in logs) never feed back into health. Failures seen at 02:36 were only blocklisted at 05:23. Others were caught at 16:22. Detection lagged by hours.
5. 11,078 of 13,886 video files have no `container_duration_seconds`, so truncation cannot be detected.

Relevant code: `internal/app/nzb_health_check.go` (`runDeepHealthCandidates`, `validatePlayableContainerDirect`, `isTransientHealthCheckErr`), `internal/nntp/fetcher.go` (position sanity check near line 236).

## Tasks

### 1. Read-failure feedback into health (suggested first)
- When a real DAV read fails with article-missing, position-mismatch, or `stored_rar layout invalid`, mark that publication for an immediate re-check instead of waiting for the next sweep.
- Needs: a hook from the DAV read-error path to the health candidate queue, with dedup so one bad file does not enqueue thousands of checks.

### 2. Per-file escalation by error count
- Count mismatch and read errors per file in a window. At N errors, run a full-file probe and blocklist and replace the release if it fails.
- Pairs with task 1.

### 3. Deeper sweep probe
- Add about 4 mid-file and tail reads to the periodic deep check, rate-limited (keep `waitForDeepHealthPacing` spacing) so the provider is not throttled.

### 4. First-segment re-verify
- Read the first article twice, a few minutes apart, to catch articles that return wrong data on some fetches. Do not blocklist on a single disagreement without a second confirmation.

### 5. Store container duration
- Populate `container_duration_seconds` for all video files (the column exists, 80% are empty). Then flag files whose readable length is shorter than the duration.

### 6. Investigate the mismatch warning burst
- About 470k `declared position is wildly inconsistent` warnings on 2026-10-08. About 360k came from one upload group during mass season-pack publishing starting ~02:52. Another part came from a player seek into a 104-volume RAR.
- Each warning is a discarded ~700 KB fetch plus a cache invalidation. Possibly large wasted provider bandwidth.
- Questions: do the constant per-file deltas come from an archive or pack offset in the expected position? Does the pre-publish check hit this and then "publish anyway"?
- Add the file or release id to the warning log line. Today it logs only the messageID, so attribution needs a slow DB scan.

### 7. Optional: database size
- DB is 5.1 GB, which is fine. Two tables hold 88%: `nzb_files.message_ids` (2.2 GB) and `nzb_documents.xml` (1.6 GB).
- Only worth doing once confirmed safe: drop stored NZB XML for old healthy items. First check what the read at `internal/database/queue_repository.go:942` uses it for.
- Small wins: 379 `nzb_documents` rows for releases with no available queue item; two `release_candidates` indexes with 0 scans (`idx_release_candidates_external_url`, `idx_release_candidates_signature`). Verify the stats were not reset before dropping.
- `message_ids_packed` exists (migration 64) but 0 of 172k rows use it.
